# GetCut 搬到微信小程序：方案调研

> 调研时间：2026-11-05
> 结论一句话：**不能移植，只能重建。** 现有出片内核是 WebCodecs，小程序和微信内置浏览器都不给这个能力。

---

## 一、先把现状说清楚

Web 端真正的出片内核不是 Remotion，是 `app/src/lib/render.ts` 里这条链：

```
Canvas 2D 逐帧绘制（draw.ts，412 行）
  → new VideoFrame(canvas)          ← WebCodecs
  → VideoEncoder.encode()           ← H.264 硬件编码
  → AudioEncoder (AAC)              ← WebCodecs
  → mp4-muxer 封装
  → Blob → 下载
```

这条链依赖 5 个浏览器能力，**小程序一个都没有**：

| Web 端依赖 | 小程序 | 微信内置浏览器（web-view） |
|---|---|---|
| `VideoEncoder` / `VideoFrame` | 无此 API | iOS 需 16.4.1+ 且只有解码；Safari 26.1+ 才补齐音视频编解码 |
| `AudioEncoder`（AAC） | 无 | iOS 长期缺失，这是「画面有、喇叭灰」的根因 |
| `OffscreenCanvas` | 有（`wx.createOffscreenCanvas`，2.16.1+） | 有 |
| `Blob` / `URL.createObjectURL` | 无，改用 `FileSystemManager` 临时文件 | 有 |
| DOM / CSS / React | 无 | 有 |

`draw.ts` 用到的 21 个 Canvas API（`fillText` / `measureText` / `drawImage` / `createLinearGradient` / `roundRect` …）小程序 2D canvas 基本都支持，**只有 `roundRect` 在安卓真机不支持**（开发者工具支持、真机报错，需手写 `arcTo` 路径）。

也就是说：**画的部分能复用，编码的部分要重做。**

---

## 二、三条路线

### 路线 A：web-view 套壳（复用现有 H5）

把现在跑通的网页直接内嵌进小程序。

**硬门槛（先卡这里，卡住就不用往下看）：**

- 微信官方原文：*「目前小程序内嵌网页能力暂不开放给个人类型账号和小游戏账号」* → **个人主体直接死路**
- 业务域名必须：HTTPS + ICP 备案 + 根目录放校验 txt + 后台「开发设置-业务域名」显式配置
- 服务器不能返回 `X-Frame-Options: DENY`

**技术现实：**

- Android：微信 X5 内核偏旧，WebCodecs 支持不确定，得真机实测
- iOS：WKWebView 跟随系统，16.4.1 起有 H.264 **解码**，但 `AudioEncoder` 直到 Safari 26.1 才完整 → **大概率出不来带声音的片子**
- 这是它自己的历史教训：`render.ts` 里那段手拼 AudioSpecificConfig 的代码，就是被手机浏览器逼出来的

**体验缺陷：**

- web-view 里不能把 MP4 存进相册，只能长按
- 不能调起微信转发卡片，得通过 `wx.miniProgram.postMessage` 回传，再由小程序下载
- 不能覆盖原生组件，全屏/导航都得放弃自定义

**工期**：1~2 天（资质能过的话）
**判定**：只配当内部试用页或引流落地页，不能当主产品。

---

### 路线 B：端上原生重建（唯一能做到离线出片）

小程序有两条被埋没的原生能力，组合起来能复刻整条链：

| 能力 | API | 关键约束 |
|---|---|---|
| 画布录制 | `wx.createMediaRecorder(canvas, {fps, videoBitsPerSecond, gop})` | 基础库 2.11.0+；**只吃 WebGL canvas**（离屏 WebGL 可以，离屏 2D 不行，webgl2 也不行）；靠 `recorder.requestFrame()` 逐帧驱动，不是实时录屏 |
| 音画合并 | `wx.createMediaContainer` | 2.9.0+；`extractDataSource` 拆轨道 → `addTrack` → `export`，可做混音 |

**改造路径：**

```
离屏 Canvas 2D 画一帧（draw.ts 原样）
  → gl.texImage2D 把 2D canvas 当纹理上传到离屏 WebGL canvas
  → recorder.requestFrame()
  → 逐帧循环
  → 拿到视频轨
配音 mp3（服务端 TTS）+ BGM → MediaContainer 拼音轨
  → export → 临时 mp4 → wx.saveVideoToPhotosAlbum
```

**硬约束清单：**

| 项 | 数值 | 影响 |
|---|---|---|
| 视频码率 | 最小 600、**最大 3000 kbps** | 现在 Web 端用 4000，要降，1080×1920 画质会掉一档 |
| 单次时长 | 最小 5s、最大 7200s | 够用 |
| 帧率 | 最大 30 | 现有 FPS=30，正好卡线 |
| 每帧数据搬运 | 1080×1920×4 ≈ **8.3 MB** | 这是最大性能瓶颈，30fps 就是 250MB/s |
| 代码包 | 主包 2MB、单分包 2MB、总包 20MB | **字体 17MB、broll 665MB 全部进不了包**，必须走 CDN |

**已知坑（动手前先记）：**

1. `roundRect` 安卓真机不支持 → 手写 `arcTo` 版
2. iOS `ctx.font` 中文字体名解析失败会渲染成 `□□□` → 强制 `sans-serif` 兜底 + `measureText` 校验
3. `wx.canvasToTempFilePath` 前必须 `await ctx.flush()`，否则 iOS 白屏/只出背景
4. 字体只能 `wx.loadFontFace` 走网络（需配 downloadFile 域名），17MB otf 建议先裁子集
5. 切后台 / 锁屏会中断录制，必须做断点续渲或提示用户别切走
6. 30fps × 1080×1920 在千元机上可能直接 OOM

**性能预估**：骁龙 8 系 60 秒片约 1.5~3 分钟；千元机 5~10 分钟，且可能崩。
**工期**：3~4 周，风险中高。

### 路线 C：云端渲染（小程序只做交互）

小程序退化成「遥控器」，出片在服务器。

```
小程序：粘文案 → 选风格 → 提交任务 → 轮询进度 → 拿 mp4 URL
服务端：现有 server.mjs / Remotion + ffmpeg 直接 Docker 化
小程序：wx.downloadFile → wx.saveVideoToPhotosAlbum / 转发
```

**成本（微信云托管官方刊例价）：**

| 项 | 单价 |
|---|---|
| CPU | 0.055 元/(核·小时) |
| 内存 | 0.032 元/(GB·小时) |
| 公网流量 | 0.8 元/GB |

2 核 4G 跑 3 分钟 ≈ **0.012 元/片**，一杯咖啡能出 2000 条。
真正的成本不在算力，在**冷启动**：Remotion 要 headless Chrome，镜像 1.5GB+，最小实例数不能设 0，否则用户等 1 分钟才开工。

**优点**：画质可控、支持长视频、能加水印、能挂付费额度、Web 与小程序共用一套渲染。
**缺点**：必须联网、有服务器运维、慢（要传文案、排队、等渲染、再下载）。
**工期**：1.5~2 周。

## 三、推荐：C 打底 + B 做预览（端上预览 + 云端成片）

| 阶段 | 做什么 | 工期 | 产出 |
|---|---|---|---|
| P0 | 小程序壳 + 云端渲染链路打通 | 2 周 | 粘文案 → 出片 → 存相册，能发朋友圈 |
| P1 | 端上 Canvas 2D 实时预览（降分辨率跑，只预览不编码） | 1 周 | 用户点风格立刻看到效果，这是转化关键 |
| P2 | 账号 / 次数额度 / 历史记录 | 1 周 | 能收费 |
| P3 | 端上离线出片（路线 B 全量） | 3~4 周 | 会员卖点：不排队、不耗流量、离线可用 |

**为什么预览要放端上**：用户在选风格那一刻没耐心。等云端渲 2 分钟才知道长什么样，留存会崩。而 2D canvas 实时画一屏（720×1280）在手机上完全跑得动——代价只是不编码而已。

**为什么不先做 B**：B 的 6 个坑每一个都能卡住一周，且低端机体验不可控。先用 C 把「能出片」这件事跑通、验证需求，再回头啃 B。

---

## 四、需要你先定三件事

1. **小程序主体**——个人 / 个体户 / 企业？个人主体直接排除路线 A。
2. **域名与服务器**——有没有已备案域名？没有的话先备案（20 天），这会影响 P0 排期。
3. **成本立场**——能不能接受每月几百块的服务器（云托管 2 核 4G 常驻约 60~120 元/月 + 流量），还是必须零服务器、只做端上离线。

答案不同，路线就不一样。见下面对话里的选项。

## 五、结论修订（与需求方确认后）

**已知条件**：个人主体、小程序已微信认证且可被搜索、已有备案域名和服务器、可复用现有域名与服务器。

### 5.1 一个必须纠正的认知

**「已认证」不等于「能用 web-view」。**

业务域名的开放与否卡的是**主体类型**，不是认证状态。官方原文是「暂不开放给个人类型账号和小游戏账号」。个人主体即使花 300 元做了微信认证，后台依然没有「业务域名」配置入口。

→ **路线 A 彻底出局，不用再考虑。**

### 5.2 好消息：云端渲染不受主体限制

小程序有两套域名，别混：

| 域名类型 | 用途 | 个人主体 | 要求 |
|---|---|---|---|
| **服务器域名**（request / uploadFile / downloadFile） | 调后端 API | ✅ 可以配 | 域名备案 + HTTPS |
| **业务域名** | web-view 内嵌网页 | ❌ 不开放 | 主体非个人 + 备案 + 校验文件 |

路线 C 全程只走 `wx.request` 和 `wx.downloadFile`，只需要**服务器域名**。个人主体完全够用。

**结论：路线 C 现在就具备全部前置条件，不需要等备案、不需要升级主体（除非要做支付）。**

### 5.3 定案

| 项 | 决定 |
|---|---|
| 出片位置 | 服务端（复用现有服务器与备案域名） |
| 渲染引擎 | `@napi-rs/canvas` 跑 `draw.ts` 同一套版面 + `ffmpeg` 合成音频，**不装 headless Chrome** |
| 为什么不用 Remotion | Remotion 要 Chrome，镜像 1.5GB+、冷启动慢；而 `draw.ts` 是纯函数，只依赖 CanvasRenderingContext2D 接口，搬到 Node 几乎零改动，镜像可压到 300MB |
| 后端基座 | 现有 `proxy.mjs`（已有账号、数据层、`data/videos` 存储、`/api/plan`、`/api/tts`），补上任务队列 + 渲染 worker |
| 小程序端 | 原生小程序（不套 Taro/uni-app），因为要直接调 `wx.*` 原生 API |
| 端上重建（路线 B） | 降级为 P3 会员卖点，不在 P0 范围 |

### 5.4 P0 工作拆解

| 顺序 | 事项 | 说明 |
|---|---|---|
| 1 | 后端 API 化 | `/api/job` 建任务、`/api/job/:id` 查进度、`/api/video/:id` 下片；把 `proxy.mjs` 的同步渲染改成队列 |
| 2 | Node 端跑通 draw.ts | `@napi-rs/canvas` + 字体注册 + `roundRect` 兼容；产出帧序列 |
| 3 | ffmpeg 合成 | 帧序列 + 配音轨 + BGM → MP4；音轨按最终时间轴铺（`lib/render.mjs` 的逻辑可复用） |
| 4 | 小程序壳 | 首页粘文案 → 选风格 → 轮询进度 → `video` 播放 → `wx.downloadFile` → `wx.saveVideoToPhotosAlbum` |
| 5 | 域名与授权 | 后台配 request/downloadFile 域名；相册需 `scope.writePhotosAlbum` 授权话术 |

### 5.5 变现路径（已核实，个人主体够用）

> 更正：本节初稿曾写「个人主体开不了微信支付」「流量主要 1000 UV」，**两条都是过期信息**。以官方文档为准，实际情况如下。

**一、个人主体可以开通「虚拟支付」**

官方文档：`开发者文档 → 平台能力 → 商业能力 → 虚拟支付:个人`
原文：*「为进一步支持个人开发者实现可持续经营，激发个人主体的创新活力，微信小程序平台将在符合条件的类目范围内，向个人主体小程序开放虚拟支付能力。」*

| 项 | 要求 |
|---|---|
| 主体 | 个人，开发者持居民身份证 |
| 服务类目 | **必须含「工具」** |
| 前置 | 已完成小程序认证 + 备案 |
| 限额 | 月支付 **10 万元** |
| 费率 | Android 等 **1%** 腾讯技术服务费；iOS **12%** Apple 佣金 |
| 排除 | 需电信业务资质的服务（邮件、语音信箱、信息发布平台、信息搜索查询等） |
| 入口 | 后台 → 支付与交易 → 虚拟支付 → 开通 → 审核约 5 分钟 → 扫码签约 |

注意这是一套**独立的「虚拟支付」**，不是传统微信支付商户号。卖的是「道具」——在小程序后台创建商品，拿到道具 ID 和价格。

**对 GetCut 恰好合适**：卖的是生成次数 / 会员，属于虚拟服务，不是实物；类目是「工具」。所有条件都对得上。

**二、流量主门槛已降到 100 UV**

2026 年 10 月 23 日起，累计独立访客（UV）≥ 100 即可申请，无刷粉、无严重违规。之前是 500。

**三、双轨变现可以直接设计进产品**

| 用户 | 路径 | 收益 |
|---|---|---|
| 免费 | 看激励视频（eCPM 最高）换 1 次生成 | 广告分成 |
| 付费 | 虚拟支付买次数包 / 会员 | 直接收入 |

这个组合和「视频生成」天然契合：生成耗时长、用户有明确等待窗口，正好放激励视频；次数是天然可计量商品，正好做成道具。

**四、两条仍需注意的红线**

1. **iOS 要被 Apple 抽 12%。** 定价要么两端同价由 iOS 用户承担成本，要么 iOS 端只卖大包/限制低价档。Android 只抽 1%，差价很大。
2. **渲染时长会顶到服务器上限。** 一条 60 秒片，Node 出帧约 3~5 分钟。2 核大概同时跑 1~2 条。要么排队，要么先限制单条时长（比如 ≤90 秒）。**这条直接决定免费额度能不能给**（广告看一次换一条，成本约 0.01 元算力，划算）。
