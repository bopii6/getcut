# GetCut 后端补齐方案：账号 / 历史 / 并发 / 付费

> 适用对象：getcut.cn 现网版本（app/ 打包后的纯静态 SPA + Caddy + 单进程 Node `proxy.mjs`，渲染在客户浏览器里跑）。
> 目标：一个后端在 **10 个工作日**内落地，不自建队列、不引 Redis、不上 K8s。
> 本文只给结论、参数和取舍，不贴代码。

---

## 0. 先看现状：这次改动的真实边界

| 现在有什么 | 这次要不要动 |
|---|---|
| 静态 SPA（Canvas + WebCodecs 浏览器出片），`/api/*` 反代到 `127.0.0.1:8790` | 不动渲染，只在关键节点加"记账"和"拦一下" |
| `/api/plan` 一次 DeepSeek 拆稿（失败已有 `rulePlan` 兜底） | 复用，加超时/重试/缓存/并发闸门 |
| `/api/tts` 一句一个请求，每句 `spawn python -m edge_tts` | **必须改**：常驻 worker + 批量 + 句级缓存 |
| 无数据库、无账号、无历史，`jobs` 是内存 Map | 新增 SQLite + 6 张业务表（另加 1 张 TTS 缓存表） |
| 成片只存在于客户浏览器内存里（Blob） | 新增"工程文件先落库、成片后落存储"两段式 |

**四条主结论（先认这四条，后面都是展开）：**

1. **账号**：匿名设备号做"试用壳"，手机号+短信验证码做"真身份"，**在付费那一刻强制绑定手机号**。不做微信登录、不做邮箱验证码（邮箱只留作短信签名没批下来时的备用通道）。
2. **历史**：成片必须上云，否则 599 买断卖的是"一次性导出工具"。默认走**对象存储直传**（不吃服务器带宽），本地磁盘只做开发/降级。
3. **并发**：单机够用，瓶颈不是 CPU 而是**出网带宽**和 **edge-tts 上游限流**。真正的性能改造只有一件事：把 TTS 从"每句一个 python 进程"改成"一个常驻进程 + 批量 + 缓存"。
4. **付费**：**卡密先行**（一码一用 + 事务条件更新 + 绑手机号），微信支付回调同一个 `orders` 表，等商户号批下来再补，不影响先卖。

## 1. 账号

### 1.1 四种登录方式的账

| 方式 | 上线周期 | 到达率（目标客户） | 单次成本 | 能找回吗 | 结论 |
|---|---|---|---|---|---|
| 邮件验证码 | 1 天（配 SPF/DKIM） | 低。律师/加盟/教培老板基本不查 QQ/163 邮件，新域名进垃圾箱概率高 | ≈0 | 能 | **只做备用**，短信签名卡住时顶 2 天 |
| 手机号 + 短信 | 1–3 天（签名报备需营业执照，你已有） | 高，国内 B 端默认动作 | 0.04 元/条，一次登录 2 条 ≈ 0.1 元 | 能，且能打电话做售后 | **主选** |
| 微信扫码登录 | 2–4 周（开放平台认证 300 元 + 企业主体 + 审核），且**拿不到手机号** | 高 | 0 | 弱（换微信就丢） | **不做**，周期不可控 |
| 匿名设备号 | 当天 | 100% | 0 | 不能（清缓存即丢） | **做"壳"**，不做身份 |

### 1.2 决定：双层身份，付费即绑定

```
弱身份（device_id，cookie，1 年）
  └─ 承载：免费 3 条额度、试用期历史、生成限流
强身份（phone，短信验证码）
  └─ 触发点只有三个：兑换卡密 / 换设备找回 / 客服处理
```

- **首次访问**：SPA 调 `GET /api/me`，服务端种 `gc_did`（HttpOnly、Secure、SameSite=Lax、1 年）。不弹任何登录框。
- **免登录体验**：device 已绑定 user 时，直接签发 session（30 天滑动，期间打开就是登录态）。
- **为什么把验证码放在付费那一刻**：599 的成交路径上多一步验证码，实测会掉 10–20% 转化；但付费前不拿到手机号，599 卖出去就是"人找不到、售后没法做、退款没法核"。把摩擦放在意愿最高的瞬间，是唯一不亏的位置。
- **顺带的好处**：手机号 = 你的私域入口。付费后立刻可加微信，这是 599 复购/转介绍的关键动作，比任何登录方式都值钱。

### 1.4 未登录能不能生成？第几条开始拦？

**能生成，免费 3 条，第 4 条拦。** 具体：

| 条数 | 未登录 | 拦截行为 |
|---|---|---|
| 第 1 条 | 全功能（5 种主题、实拍空镜、1080×1920） | 无 |
| 第 2–3 条 | 同样全功能，**片尾 3 秒水印 + 右下角小标** | 无 |
| 第 4 条 | 拒绝 | `/api/gen/start` 返回 402 + `reason=quota`，前端弹"输入卡密 / 购买"，**不封页面**，并把已生成的 3 条摆出来当作品集 |

设计要点（每一条都是防坑）：

- **额度在"开始生成"时扣，不是渲染完扣**。否则并发开 10 个标签页就能白嫖 10 条。扣完失败自动退还（见下）。
- **登录不送额度**。否则客户注册两个号就是 6 条。登录只做一件事：把设备上的额度和历史迁到账号。
- **失败退还**：`gen` 状态转 `failed` 时退 1 条；每设备每天最多退 1 次，防"故意失败刷额度"。
- **技术限流（付费也受）**：10 条/小时、30 条/天。599 是买断不是买服务器，这条线必须有，但设置得让正常客户永远碰不到。
- **免费 3 条的成本**：3 ×（拆稿 2–5 分钱 + 存储流量几分钱）≈ 0.1–0.2 元/试用客户。**别为了省这点钱把免费额度做成 1 条**——599 的成交靠客户看到成片质量，3 条才够他试出"这个能发"。

### 1.5 会话与安全（不展开成安全方案，只列必须做的）

- Cookie：`HttpOnly` + `Secure` + `SameSite=Lax`，域 `getcut.cn`。前端拿不到 token，XSS 也偷不走。
- 短信：同号 60 秒 1 条、10 条/天；同 IP 20 条/天；验证码 5 分钟有效、错 5 次作废；同一 IP 1 小时内验证码登录 > 20 次直接拒。
- 会话固定期内不轮换 token 可以接受；退出登录 = 写 `revoked_at`。
- 手机号是个人信息：隐私政策里写清"用于登录、售后、订单"，提供注销（真删手机号）。客户是律师，这点别省。

## 2. 历史记录

### 2.1 视频文件存哪：三种方案的成本账

先定基准：60 秒 1080×1920 @ 4Mbps ≈ **25–30MB/条**。100 个客户 × 20 条 ≈ **50GB**。

| 方案 | 钱 | 风险 | 结论 |
|---|---|---|---|
| **只让用户本地保存** | 0 | 换电脑/清缓存/换手机就全丢；客服无法帮客户找回；599 买断变成"一次性导出工具"，退款理由现成 | ❌ 只能作为**兜底**（每条都提供下载），不能是唯一 |
| **服务器本地磁盘** | 云盘约 0.3 元/GB/月，50GB ≈ 15 元/月，可忽略 | **吃服务器带宽**：5Mbps 峰值带宽下，10 个客户同时上传 270MB 要 7 分钟，期间所有人变卡；磁盘打满会拖死 Node；扩容要停机 | ⚠️ 仅当带宽 ≥ 20Mbps 或客户 < 30 时可用，作为开发/降级方案 |
| **对象存储（OSS/COS/S3 兼容）** | 标准存储 0.12 元/GB/月 → 50GB ≈ 6 元/月；出网 0.5 元/GB，按每人重下 3 次 ≈ 25 元/月 | 多一个云账号、CORS、预签名配置（约半天） | ✅ **默认选它** |

**决定：对象存储直传（浏览器 → OSS，用服务端签发的预签名 PUT）。**

理由不是单价（单价三者都便宜），而是：

1. **不吃服务器带宽**。2C4G 轻量机的 5Mbps 是这次最稀缺的资源，成片上传/下载不该走它。
2. **生命周期规则**直接解决保留策略（90 天自动删），不用自己写清理任务。
3. **下载走 CDN/直链**，客户点"重下"不占你 CPU 和连接。

**代价与对策**：预签名不能裸发。签名必须绑定 `gen_id` + 固定 key + `content-length` 范围（10–45MB）+ `content-type: video/mp4`；上传完服务端 HEAD 校验 size 再置 `video_key`。这样别人拿到签名也只能传一条视频到指定位置。

**代码层面只留一个 `storage` 接口**（`put/getUrl/delete`，两个实现：local / oss），切换只改配置。这是唯一值得提前抽象的地方。

### 2.2 上传链路：先落"记录"，再落"成片"

这是整个历史功能最关键的一个设计，因为它决定了"客户生成完就关页面"会不会丢东西。

```
点生成 → POST /api/gen/start（扣额度、建记录 status=running，返回 gen_id）
       → /api/plan（带 gen_id）
       → /api/tts/batch × 3~4 批（带 gen_id）
       → 浏览器渲染出 MP4（客户此刻已可下载）
       → POST /api/gen/finish（小的 JSON：beats、时长、cover 上传）→ 记录立刻 status=done
       → 后台异步：预签名直传成片 → 确认 → 回填 video_key
```

- **finish 只传几百 KB 的 JSON 和一张封面**，秒回。此刻历史列表里已经有这条了。
- **成片异步传**。客户 4G 上行 25MB 要 1–2 分钟，不阻塞体验；传完显示"已保存到云端"。
- **如果客户在上传完成前关了页面**：记录在、`video_key` 为空，列表显示"成片未保存"，给一个**"重新生成"**按钮（用 `beats_json` + TTS 缓存重渲，1–2 分钟）。这比"记录直接消失"体面得多，成本几乎为零。
- 前端在 `beforeunload` 里不要做伪同步上传（`sendBeacon` 传不了 25MB），接受这个降级。

### 2.3 保留策略

| 客户类型 | 条数 | 时长 | 单条上限 | 过期后 |
|---|---|---|---|---|
| 免费（未付费） | 3 条 | 7 天 | 90 秒 / 40MB | 成片删，记录留 30 天，显示"已过期" |
| 付费（pro） | 最近 100 条 | 90 天 | 90 秒 / 40MB | 成片删，**工程文件保留 1 年**，可一键重渲 |
| 单账号总量 | — | — | 3GB 软上限 | 超出按最旧删成片，保记录 |
| TTS 缓存 | — | 60 天未使用即删 | 总量 5GB | — |

- **"成片过期但记录还在"是 599 买断的关键体验**：客户三个月后翻到 2026 年的案子，点一下还能出片，只是多等 2 分钟。这比"什么都没有"值钱得多，而存储成本是 0（只剩几 KB 的 JSON）。
- 清理任务：每天 03:00 跑一次，扫 `status='done' AND expires_at < now`，删文件 → `status='expired'`；顺手清 `tts_cache`。
- **别做回收站**。客户是律师，删除要真删（记录 + 文件 + 缓存引用一起清），这本身就是卖点。

### 2.4 列表：字段与操作

**卡片字段**（前端一次拿全，不做二次请求）：

`id`、`title`（首句前 14 字，超长截断）、`cover_url`（有则显示，无则主题色渐变占位）、`created_at`、`duration`（如 0:58）、`size`（如 27MB）、`status`（已完成 / 生成中 / 失败 / 已过期）、`has_watermark`、`video_url`（签名 24h）或 `regenerate`（可重渲标记）。

**操作（4 个，不多不少）**：

| 操作 | 行为 | 备注 |
|---|---|---|
| 重下 | 302 到 24h 签名 URL，文件名 `getcut-20261104-首句标题.mp4` | 客户要的是"能直接发抖音"，文件名带日期很实用 |
| 再来一条 | 把 `text / theme / voice` 填回工作台，**不自动开始** | 避免误扣额度；客户 90% 是想改两句再出 |
| 删除 | 软删记录 + 异步真删文件，列表立刻消失 | 二次确认，文案写"删除后不可恢复" |
| 播放 | 列表内联播放（首帧封面 + 点击加载） | 别自动加载 25MB 视频，列表会卡死 |

**分页**：cursor 分页，20 条/页，按 `created_at DESC`。
**第一版不做搜索**：几十条记录，客户靠封面和时间就能找到；超过 100 条再加标题搜索。

## 3. 并发

### 3.1 现在的实现会怎么炸（4 个具体 failure mode）

1. **每句一个 python 进程**。20 句 = 20 次 `python -m edge_tts` 冷启动（每次 0.5–1 秒 + 50–80MB 内存）。10 个客户同时点 = 200 个进程 ≈ 12–16GB 虚拟内存申请，2C4G 直接 OOM，`proxy` 被系统 kill，**所有人生成失败**。
2. **浏览器串行 20 次 RTT**。`voiceAll` 是一句一句 `await`，单条配音就 30–60 秒；10 个客户在 30 秒窗口里挤进 200 个独立请求，没有队列，全打在上游。
3. **没有超时/重试/降级**。edge-tts 抖一下（微软免费接口常事），整条失败；客户点重试 = 又一轮 20 个进程。
4. **大 body 读进内存**。将来加 25MB 上传，10 并发 = 250MB 峰值 Buffer，加上渲染中的页面，内存曲线会很难看。

### 3.2 三层闸门

| 层 | 参数 | 超时 | 超出时行为 |
|---|---|---|---|
| 接入（Caddy） | `/api/*` body ≤ 1MB（Caddy 原生 `request_body` 限制；成片走 OSS 直传，不经过它）；`/media/tts/*` 与静态资源由 Caddy 直出 | — | 413 |
| 应用（Node 队列） | **生成并发 8**；队列上限 20；**同一 user/device 同时只能 1 条 running**；单 IP 并发 ≤ 20；上传并发 2（仅本地磁盘模式） | 排队等待 ≤ 90 秒 | 超时返回 429，`retry-after` + 中文"现在人多，前面还有 N 位" |
| 上游（信号量） | DeepSeek 4；edge-tts 6（在 worker 内部，见 3.3）；Pexels 空镜 2 | 见 3.4 | 退避重试 → 降级 |

- **队列用进程内数组**，不用 Redis、不用 BullMQ。理由：单机单进程，重启丢队列是可接受的（正在跑的最多 8 条，重启后客户重试即可）；引 Redis 会多一个要运维、要备份、会挂的组件。
- **per-actor 只允许 1 条 in-flight**：客户开了 3 个标签页点生成，第 2、3 个直接被拒（"还在生成上一条，等一下"），这比排队 3 条更符合直觉，也省上游。
- **队列要能被看到**：`/api/job/:gen_id` 返回 `{queue_position, eta_seconds}`，前端显示"前面还有 2 位，约 40 秒"。这句话能把 90% 的"怎么不动了"客服消息消灭掉。

### 3.3 TTS 改造（收益最大的单点，半天工作量）

**改法：一个常驻 python worker 进程，Node 通过 `127.0.0.1:8791` 调它。**

- worker 内部 `asyncio.Semaphore(6)` 做全局并发上限，一次请求收 5 句，并发合成、合成完一起返回。
- 省掉每次 0.5–1 秒的 python 冷启动；内存从"200 × 70MB"变成 **1 × 80MB**；进程数从 N 降到 1，OOM 风险归零。
- **为什么是 5 句一批、不是 1 句也不是 20 句**：1 句 = 20 次往返 + 没有进度；20 句一次 = 一个 40 秒的大请求，任何一句失败全批重来，且前端看不到进度。5 句 = 4 个请求、进度条动 4 次、失败只重试 5 句。

**edge-tts 单机并发定多少？起步 6，压测到 8 为止。**

- 依据：微软这个免费接口按 IP 有软限流，经验值 4–8 条并发稳定；**超过 10 开始出现 403 和连接重置**。这不是 CPU 限制（1 句只有 30–60ms CPU），是上游策略。
- 压测方法（半天）：用 20 句真实文案跑 10 轮，并发分别设 4/6/8/10，看失败率。失败率 < 1% 的档位就是你的上限，写进配置，别写死。
- 必须加：单句 15 秒超时、429/5xx 退避重试 2 次（1s/2s + 100ms 抖动）。抖动很重要，否则 6 个并发会同时重试，二次撞击上游。

**句级缓存（免费的性能）**

- key = `sha256(voice | rate | text)`，值 = mp3 文件。命中直接返回 `/media/tts/<hash>.mp3` 静态 URL（让 Caddy 直接发，`Cache-Control: immutable`），**根本不进 worker**。
- 命中率预估 **20–40%**：同一客户改稿会重说一半句子；同行业客户（加盟、律师）的套话高度重合（"今天讲三个数""把品牌名发给我"）。
- 顺带把整段拆稿也缓存 24 小时（key = 文案 hash）：客户手滑刷新重来，不重复烧 DeepSeek 的钱，也不重复占并发。

| | 改造前 | 改造后 |
|---|---|---|
| 20 句进程启动开销 | 10–20 秒 | 0 |
| 10 并发内存峰值 | 12GB+（必然 OOM） | 约 80MB |
| 单条配音耗时 | 30–60 秒（串行） | 12–20 秒（4 批 × 6 并发 + 缓存命中） |
| 上游失败整条报废 | 是 | 否，单句降级 |

### 3.4 超时 / 重试 / 降级 / 客户看得懂的话

| 调用 | 超时 | 重试 | 最终降级 |
|---|---|---|---|
| DeepSeek 拆稿 | 45 秒 | 2 次（1s/3s 退避，429/5xx 才重试） | **已有的 `rulePlan` 规则拆稿**，前端提示"AI 拆稿忙，已切规则版，画面会糙一点" |
| 单句 TTS | 15 秒 | 2 次 | 该句用**静音 + 按字数估时长**占位，成片照出，提示"第 7 句配音失败，已用静音" |
| 一批 5 句 | 45 秒 | 0（内部已重试） | 同上，不影响其他批 |
| 整条生成 | 5 分钟（前端 watchdog） | — | 判 failed、**退还额度**、提示重试 |
| 服务端 gen 记录 | 10 分钟未 finish | — | 自动转 failed + 退额度（防止客户关了页面把并发槽占死） |

**错误文案（直接抄，别让客户看到 "500"）：**

- 排队：`现在人多，前面还有 3 位，大约 40 秒后开始。中途关掉页面不会扣次数。`
- 上游抖：`配音服务刚才没响应，已经重试过 2 次。可以再点一次生成，这次不扣次数。`
- 超长：`这段 1800 字，出来要 7 分钟、文件 90MB，建议切成 2 条发。`
- 浏览器不支持：`这个浏览器不能编码视频，换最新版 Chrome 或 Edge 就行（手机上不行）。`

原则：**任何失败都要告诉客户"扣不扣次数"**。这是 599 客户最在意的，也是投诉率最高的点。

### 3.5 10 个并发、每人 20 句，2C4G 扛不扛得住？

**扛得住。但先看清一件事：服务端只占客户等待时间的 1/4 到 1/3。**

单条时间构成：拆稿 10–15s + 配音 15–25s（服务端）→ 浏览器渲染 90–180s（客户自己的机器）。所以 10 个客户同时点，服务端在 40 秒内就把活干完了，剩下 3 分钟是各自的浏览器在跑。**天然错峰**。

| 资源 | 10 并发峰值估算 | 2C4G 余量 |
|---|---|---|
| CPU | 拆稿纯等待（≈0）；TTS 140 句 × 50ms ≈ 7 秒；Node 序列化 + 静态分发 ≈ 5 秒 → 峰值约 **1.2 核** | 够，还有 40% |
| 内存 | Node 250MB + worker 80MB + SQLite 64MB + Caddy 50MB ≈ **450MB** | 4G 非常富余 |
| 出网带宽 | 成片 10 × 27MB = **270MB**：走服务器 5Mbps 要 7 分钟（❌）；走 OSS 直传 ≈ 0 | **这是唯一真瓶颈** |
| 上游配额 | DeepSeek 10 次（闸门 4，约 3 轮 ≈ 35 秒）；edge-tts 140 次（6 并发 ≈ 35–45 秒） | 看账号 RPM/TPM，需实测 |
| 磁盘 IO | TTS 缓存约 8MB/轮；成片不落盘 | 无压力 |

**结论：瓶颈排序 —— ① 出网带宽（成片上传/下载）② edge-tts 上游限流与抖动 ③ DeepSeek 的 RPM/TPM 配额。CPU 和内存都不是问题。**

所以 2C4G **够用**，但必须同时满足三个前提：TTS 改常驻 worker、成片走对象存储、空镜默认关闭。三条缺一条，10 并发就会变成事故。

### 3.6 隐藏杀手：实拍空镜

打开"配实拍空镜"后，每条要按关键词去 Pexels 抓 8–20 个竖屏视频，单个 5–15MB → **单条成片可能要下 100MB+ 素材**，10 个客户 = 1GB 全部穿过你 5Mbps 的代理。这不是慢，是直接堵死所有人。

对策（都很便宜）：

1. **默认关闭**（现在就是默认关，保持）。
2. **关键词级落盘缓存 7 天**（现在只有 24 条内存缓存，重启即丢）：`broll/<sha1(keyword)>.mp4`。加盟/律师行业关键词高度重合，第二轮开始命中率能到 60%+。
3. **每条最多取 6 个素材**，只挑 540p 档位（现在逻辑已经是挑 540 宽，保持）。
4. 并发闸门 2，超出排队。

**做这四条，空镜就从"带宽炸弹"变成"一个会命中缓存的可选功能"。**

## 4. 付费解锁（599 买断）

### 4.1 卡密还是支付回调？

| | 卡密 | 微信支付回调 |
|---|---|---|
| 上线时间 | **1 天** | 2–6 周（商户号 + 企业资质 + 域名备案一致性 + 回调验签 + 退款流程） |
| 收款方式 | 微信/支付宝个人或对公收款，人工发码 | 自动到账 |
| 适合客单价 | 599 这种低频高客单，人工发码完全撑得住 | 高频低客单必须 |
| 风险 | 发码延迟（承诺 1 小时内）、客服工作量 | 资质卡住就上不了线 |

**决定：卡密先行。** 理由很简单：两周的工期里，微信支付商户号是最不可控的一项，而 599 的客单价意味着"人工发码"完全不是瓶颈（一天卖 10 单也就 10 次复制粘贴）。`orders.channel` 预留 `wechat`，等资质下来直接接，表结构不用改。

**建议的卖法**：落地页留"我要买" → 加微信 → 收款 → 发码（人工或自动发货工具）。这个动作用户体验甚至比自助支付更好，因为你能顺手问一句"你是做哪行的"，拿到定位信息。

### 4.2 卡密生成

- 离线脚本 `gen-cards.mjs --count 100 --batch 2026-11-A`，跑在服务器上，不进 Web 后台。
- 格式：**`GC-XXXX-XXXX-XXXX-XXXX`**（16 位，4 位一组，好念好抄），字符集用 Crockford Base32（去掉 I/L/O/U，避免和 1/0/V 混淆）。
- **15 位随机 + 1 位校验位**（本地可算）。搜索空间 32¹⁵ ≈ 3.8×10²²，配合"先校验位、后查库"，爆破在第一步就死。
- 输出：CSV（code, batch, sku）+ 可选一页 A4 可打印（方便线下发）。
- 作废：批量 `status='void'`，已发出的作废要记 note。
- **不要做"卡密绑定套餐/时效"**，第一版只有一种卡：`pro_lifetime`。

### 4.3 核销链路（7 步，一步都不能省）

1. **客户入口**：历史页上方常驻"输入卡密"入口，以及第 4 条被拦时的弹窗里。
2. **前端预处理**：自动大写、去空格和横杠、按 4 位分组显示。这一步能挡掉一半手误。
3. **服务端先算校验位**（不查库）：格式不对直接返回"卡密少了一位/有错字"，**不消耗任何限流额度**。
4. **必须已登录**：未登录 → 先走短信验证码登录，待核销的 code 暂存 `sessionStorage`，登录后自动继续。**卡密绑到 `user_id`，不绑设备**——这样客户换手机、换电脑，用手机号登录就还在。
5. **事务核销**（核心）：开一个立即写事务，对 `card_keys` 执行一条**带 `status='unused'` 条件**的更新（写入 `used_by_user_id`、`used_at`），**检查影响行数是否为 1**：
   - 行数 = 1 → 事务内继续写 `orders`（`status='paid'`，`channel='card'`）、更新 `users.plan='pro'`、`pro_since`、`pro_order_id` → 提交。
   - 行数 = 0 → 回滚，说明已被用/已作废，返回对应提示（不告诉他是谁用的）。
   - **为什么这样就不会重复**：SQLite 单写事务 + 条件更新是原子的。两个请求同时到，数据库自己排队，第二个的影响行数必然是 0。**不需要分布式锁、不需要 Redis，这就是单机方案最大的便宜。**将来迁 Postgres 时，同一句 `UPDATE ... WHERE status='unused'` 照样成立，迁移零成本。
6. **幂等**：同一用户重复提交同一 code → 查 `orders` 里已有该 `card_id` + `user_id` 的 paid 单 → 直接返回 200"已解锁"，不报错。客户刷新页面、连点两次都不会出问题。
7. **防爆破**：同 IP 10 次/小时 → 429 一小时；同账号 5 次/10 分钟；连续失败加 300ms 延迟。

### 4.4 免费额度怎么给、怎么防刷

| 手段 | 挡什么 | 代价 |
|---|---|---|
| 额度记在服务端 `devices.free_used`，前端只做展示 | 改 localStorage、刷新重置 | 无 |
| `gc_did` cookie + localStorage 双写，不一致时以服务端为准并重发 | 单纯清 localStorage | 无 |
| 同 IP /24 在 24 小时内出现的新设备 > 2 个 → 新设备只给 1 条 | 无痕模式刷额度 | 误伤共用 WiFi 的小概率正常客户（可人工补偿） |
| UA + 时区 + 屏幕尺寸做轻指纹，同指纹换设备号 → 沿用旧额度 | 换浏览器刷 | 无（**不做 Canvas 指纹**，隐私和复杂度都不值） |
| 付费客户不受设备限制，登录即恢复 | — | — |
| 30 条/天 + 10 条/小时（付费也受） | 脚本跑量 | 正常客户碰不到 |

**取舍说明**：免费 3 条 + 上面这套，能挡住 95% 的薅羊毛；剩下 5% 的成本是每条 2–5 分钱，**不值得为它做设备指纹风控系统**。真出现批量刷，看日志封 IP 段即可。

### 4.5 权益生效与降级

- 解锁后：去水印、历史 90 天/100 条、空镜可用、不限条数（仅受技术限流）、优先队列（付费客户排在免费前面，这是免费的体验差异）。
- 退款：`orders.status='refunded'` + `users.plan='free'`（**手动操作，脚本一条命令**），历史保留但只能下载已生成的，不能新生成。**不做自动退款**——599 低频，人工处理反而不会出错。
- 封号：`users.status='banned'`，所有 session 置 `revoked_at`，请求直接 403 + "账号已停用，联系客服"。

## 附录 B：部署与备份（别省这半天）

- `getcut-api.service` 扩成"Node 主进程 + TTS worker"两个 unit，worker `Restart=always`，只监听 `127.0.0.1:8791`。
- 数据全在 `/opt/getcut/data/`（`app.db` + 本地模式下的视频）。
- **备份**：每小时 `sqlite3 .backup` 到 `/opt/getcut/backup/`（保留 7 天滚动），每天 rsync 一份到另一台机器或对象存储。**SQLite 单文件丢了就是客户全丢**，这是 599 买断最不能出的事故。
- 日志：Caddy access log 保留 7 天；应用日志只记 `gen_id / user_id / 阶段 / 耗时 / 错误码`，**不记文案原文**（律师客户的隐私）。

## 附录 C：5 个监控指标（超阈值就该动手）

1. 生成失败率 > 3%（按小时）
2. 生成 P95 > 120 秒
3. 队列深度持续 > 5（说明 8 个并发槽不够，或上游变慢）
4. TTS 单句失败率 > 2%（说明并发开太高，被上游限流）
5. 磁盘 > 80% / 月出网流量 > 流量包 70%
