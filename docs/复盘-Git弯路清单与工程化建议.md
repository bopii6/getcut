# 从 Git 历史里挖出来的弯路 —— 2026-09-15 ~ 09-23（150 个提交，9 天，统计截至 9/23 13:00）

> 这份东西只用了两样：`git log` 和这个仓库现在的文件树。**没有引用任何一次聊天记录**，所以 ZCode、别的编程工具里绕的路，只要落进了提交，就都在下面这些数字里。每条弯路后面都能自己敲命令复现（最后一节）。

## 一、先给三句结论

1. **这个项目定得最晚的一件事，恰好是最早该定的那件**：片子最终在谁的机器上渲出来。9/15 定云端，9/20 才定浏览器 —— 中间 5 天里为云端写的东西，绝大部分被删了。
2. **自动检查（闸门）出现在第 101 个提交，不是第 3 个。** 前面那 100 个提交的代码，全靠人肉看一眼网页来保证没写坏。
3. **提交消息里出现「重做 / 退役 / 下线 / 拆除 / 不再 / 真机才暴露」，都是同一件事的马甲**：前一天写下的是想法，不是决定。这类词在项目里出现了 25 次。

打个比方：这 9 天像一辆车在高速上换过五次方向盘位置。每次换的理由都对，但真正的成本不是拧螺丝，是那五次都忘了先定「这车到底是拉货还是载人」——那个定下来，方向盘只调一次就够。

## 三、八条弯路，每条带证据

### 弯路 1：主变量最后才定 —— 出片这件事换了五次住处

**证据（按时间）**

- 9/15 23:40 云端渲染起步：GitHub Actions 渲染机 + Cloudflare Worker 网关
- 9/16 12:26 `c2e7299` 迁腾讯云 4C4G；23:48 `81f2d7d` 删掉 Actions 渲染链路（−687 行）
- 9/19 13:14 `009af07` 双通道流水线 + 付费插队 + 并发 2
- 9/20 08:59 `61bd7bf` 编舞引擎 + **分布式渲染工人节点**（+2212 行）
- 9/20 19:56 `bba1200` **浏览器成片台**：渲染混音全搬进客户浏览器（+2179 行）
- 9/20 20:36 `14a6d52` 云端渲染与 Node 渲染台退役（−1393 行）
- 9/23 09:26 `ad31cdf` 下线 /studio 工作台

**代价**：删掉的文件里躺着一整套渲染工人（rendernode.py）、一份 docker-compose.node.yml、云端 Worker 与 GH Actions 链路。粗算 3000+ 行属于「先写后删」，其中 2212 行活了 **11 小时**。

**病根**：「渲染放在哪台机器」是这类产品**唯一会牵动全局的成本变量**——它决定带宽谁付、并发几个人能同时出片、失败算谁的、要不要排队、怎么收费。这个变量本该用半天做一个丑但真实的验证（本机跑一次 1080×1920 要多久、多少内存、客户那边浏览器能不能扛），当天定死。它被留到第 6 天（9/20）才定，于是前面每次「顺手优化」都在给一个必将被推翻的架构打地基。

**下次的规矩**

- 开工第一周，先找出**那个一改全盘改的变量**（本项目=出片在哪跑；别的项目=数据放谁的库、钱怎么算、内容谁生成），花半天做一个不求好看只求真实数字的 spike，写进 `README` 的「架构决定」小节。
- 决定要写成一行字 + 日期 + 依据。换方向时不许悄悄换：**新增一条决定，并写明前一条为什么作废**。项目里「分布式渲染工人节点」到「浏览器成片台」之间，没有任何一句书面理由，只有当天的一次大提交和一次大删除。
- 未定之前，只做「搬到哪都不用重写」的那层：素材包协议、字幕与配音对齐、模板版式。这几样本项目从头用到尾，是全项目最划算的投入。

- 9/21 19:51 `db8770e` 五套主题的小字对比度全部重调到 4.5:1 以上

**代价**：与界面直接相关的提交 **50 个，占全项目 1/3**。五套主题系统本质是给「还没定稿」上保险——它把一次决策推迟了 4 天，代价是每次换方向要乘 5。

**病根**：视觉方向不是工程问题，靠改代码不会变清楚。深夜时段判断力最低，做的偏偏是最不可逆的审美决策，第二天醒来又要拿令牌层去补。而且客户的审美是有锚点的（40~50 岁、「简洁中有贵重」），锚点没写成一句话就开工，每套新方案都像是「对的那个」。

**下次的规矩**

- **先出 3 张静态样张图，选定后 CSS 令牌封版**。样张是图，不是代码；改图的成本是 5 分钟，改代码是 4 天。方向没定就在代码里做主题切换，是把决策成本转嫁给了后面所有提交。
- 一条审美锚点写成一句话贴在最前面（例：「像高端杂志内页，不像互联网公司后台」）。凡是和这句话冲突的方案，看都不用做完。
- **00:00 之后不做不可逆决策**——这条不是养生，是纪律。凌晨那 18 个提交里，第二天需要补的第二轮改动的比例最高。

### 弯路 3：自动检查第 101 个提交才装，于是「话带了、码没带」

**证据**

- 9/21 18:02 `9cae7ec` 后端 184 条 + 前端 35 条离线闸门；18:03 `5c0771f` CI 门禁 —— **第 100/101 个提交**
- 同一天 23:13 `b21bfb7`：「掉线修复正文这次真的入库 —— 上次提交只带了话没带码」；23:13 `9f6a1db`：「补交 run_backend.sh 与试玩额度回归测试，CI 真正回绿」
- 测试文件数曲线：9/17 就有 4 个测试文件，之后**四天不动**（9/20 仍是 4）

**代价**：闸门装上之前，100 个提交、约 5 万行代码（9/15–9/20 合计 +49,490 行）是在没有回归网的状态下写的；装上之后**当天**就抓出四条 P0（《项目最佳实践评估》§7 那批：路径穿越可伪造管理员会话、会话不可吊销、存储型 XSS、试玩额度可无限刷）。

**病根**：闸门不是「有空再加的质量项」，它是**提交这一动作的质检流水线**。没有它，一次提交是不是完整，只能靠人记得「我刚才改了哪三个地方」；AI 会话越多，记不住的概率越大。所以「话带了码没带」和「CI 一直是红的却没人知道」必然发生——它们是缺闸门的必然结果，不是粗心。

**下次的规矩**

- **第 3 个提交就装三样**：一条本地自测命令（哪怕只断言 5 件事）、一条 CI 跑它、一个提交前快闸（ruff/tsc 级别）。半天就够，之后每个功能都自动多一条断言，闸门会自己长大——本项目 4 → 26 个测试文件全发生在 9/21 之后。
- 提交完就 `git show --stat HEAD`，三秒钟，专治「话和码分家」。
- **闸门要红过才算装上**：故意写坏一处，看它拦不拦。本项目 CI 是补交 `run_backend.sh` 之后才「真正回绿」——反过来说，之前那次「绿」是假的。

### 弯路 4：信任边界第 7 天才画，四条 P0 都藏在那张没画的表里

**证据**

- 9/17 00:17 `3bcc178` 才加邮箱密码登录（此前是令牌）
- 9/19 09:21 `8b4400e` 上线前审查修复（成片越权 P1 / 验证码限流）
- 9/21 11:45 `456da8c` 密钥三件套搬出工作区；18:01 `1c227be` 限流与试玩额度**不再认客户端自填的 IP**；18:25 `6a99ae6` **管理员只认邮箱白名单，不再「谁先注册谁是管理员」**

**代价**：6 天里每个「先让它能跑」的多用户假设，第 6 天都要在接口层返工。而「谁先注册谁是管理员」这种设计，只要多用户第二个人登录过就会暴露——它一直活到第 7 天。

**病根**：安全被当成了一层可以后加的涂层，其实它是**数据模型的一部分**。谁能看谁的成片、额度算在谁头上、管理员怎么产生，这三条不写清楚，代码就必然写成「先按只有一个用户想」。注意 `1c227be` 那条：限流认了客户端自报的 IP——这类 bug 不是漏写校验，是压根没问过「这个数该谁说了算」。

**下次的规矩**

- 动手前写半页**信任边界表**：资源（成片/素材/账号/额度）× 角色（主人/其他客户/匿名/管理员）× 操作（读/写/删/计费）。每格写「服务端凭什么放行」。这张表能预先否掉本项目后来那四条 P0。
- **凡影响钱的数，一律服务端算**，客户端递来的身份/额度/IP 一律当不可信输入。
- 密钥、会话、用户数据这三样，Day 0 就规定存在**工作区之外**的路径（本项目最后落到了 `/state`，但为此返工了三次）。

### 弯路 5：把外部服务自报的数当成真值，一个坑连拍六次

**证据（字幕 ↔ 配音对齐，全在 9/22 一天）**

- 10:44 `dd061da` 词级时间戳按文本对位 → 13:26 `9802579` 估算兜底锚定句首 + 加对齐闸 → 17:51 `08946d4` 落地对齐评分器 → 18:10 时间轴改用自听配音的逐字时刻 → 18:40 `b07e508` 扣掉字头比声音起振早的量 → 20:45 `b7b50b4` **不再采信任何服务端时间戳**

**同类**：声音复刻 9/19 10:42–11:26 五连修（`e44912d`/`26ceda7`/`41b771a`…）；环境自检 9/23 一小时内改了四次（10:48 `62897ff` → 11:14 `456f13b` → 11:28 `66a5b96` → 11:41 `a71cff3`，最后一条才把技术徽章换成「一键体检、三档结论」）。全项目提交消息里「根治」出现 4 次、「真机」3 次。

**代价**：一天 6 个提交在同一个问题上打转，最后一个才写清真正的结论：**上游给的逐字时间戳是编出来的假数据**。前 5 次都是在这份假数据上找偏移量。

**病根**：外部 API 自报的度量（时间戳、时长、进度百分比）看起来最像事实，所以最容易被当成真值。一旦当真值，你看到的偏差就会长得像「偏移」，于是你修偏移；可它其实是噪声，永远修不完。**最后一次提交才第一次自己造真值**（自己听自己的配音）。同一天的 6 个 fix 就是这条弯路的全部形状。

**下次的规矩**

- 凡是要用外部服务给的「数」，第一步先花半天**自己造一个地面真值**，量一次偏差直方图（最大/中位/分布形状）。分布没形状=数据不可信，直接自己算。
- **第二次补丁还没解释清现象，就停止打补丁**。规则：同一症状，第二次修必须换一个假设，而不是把上次的算法调细。
- **阈值/规格类判断（例：视频 level、硬件能力、超时时长）必须用真实参数算一遍**，别用「常见默认值」。`66a5b96` 那条只有 26 行改动，前面是 3 小时排查 + 客户看到的一张假警报黄牌。

### 弯路 6：多个写者同时对一份工作区动手，部署脚本还会整目录删

**证据**

- 9/21 19:36 `c048836` 记录上线当晚两次现场修，其一是「**整包对齐误删服务器独有资产**」
- 9/22 17:33 `216e7a0` chore(护工)：把在途的字幕同步改动**锁成检查点，防被并行会话抹掉**
- 9/21 19:14 `10d02e3` 模板样片与展示字收进版本库，**部署脚本的删除范围收紧到 .py**；19:17 `6410d0e` 改成只传有变化的文件（「16MB 整目录一次推会被这条链路掐断，实测截断过 sample-poster.mp4」）
- 部署入口今天还有三个并存：`videogen/deploy.sh`、`videogen/tools/deploy_new.sh`、`videogen/tools/deploy_to_prod.sh`（第四个 `deploy_git.sh` 已删）。

**病根**：两个方向的同一个错——**在工作区外面留了「只有那台机器才有的东西」，又用「对齐」的方式同步**；以及**两个会话共用一份文件树**。前者必然误删，后者必然互抹。项目最后是靠「先给对方在途改动打一个保护性提交」绕过，那是止血不是治。

**下次的规矩**

- 服务器上**不允许存在仓库里没有的东西**：资产入库、配置进环境文件、密钥进 `/state`。做到这条，「整包对齐」就从危险变成安全，回滚才有意义。
- **一个工作区同一时刻只有一个写者**；要并行就开 `git worktree` 或分支，各写各的目录。这条要写成硬规矩，不能靠记着。
- 部署脚本的删除动作要显式白名单 + 保留一份可回退的位置。默认只增不删。
- 只留**一个**部署入口，其余删除。四个并存 = 下一次上线要用哪一个，全靠猜。

**下次的规矩**

- 排序口诀：**能手动做的先手动做 1 次，做 2 次的写脚本，做 10 次的才写进产品。** 只有进了产品的那一层才写架构。
- 一个只给自己用的接口（MCP/Agent）不进主仓库主线，另开分支或独立小工具；验证完再合，验证不过就丢。
- 定价/支付方式在收到第一笔钱之前**只留一种**。多档位=多套权益代码+多套文案+多次返工，本项目三档收敛成一档用的就是这个价。
- 架构层的扩容（并发、队列、分布式），触发条件写成一句可观测的话：「连续两天有客户排队等待」。**不出现就不做**。

### 弯路 8：把仓库当百宝箱 —— 产物、素材、密钥混在同一条路上

**证据**

- 9/21 13:06 `8554f8c` 前端产物纳入版本库（为「推 GitHub 就能部署」）→ 一次提交 +287,748 行；`.git` 现在 144MB，其中 `server_static/poc/bundle.js` 同一路径被提交 **15 次**、每份约 3.7MB
- 9/16 23:48 运行时状态文件移出版本库；9/18 09:27 忽略密钥、registry.json 停止跟踪；9/21 11:45 密钥搬出工作区 —— **`.gitignore` 一共改了 7 次**，都是补
- 仓库根目录今天躺着 **13 个 zip/mp4，共 609MB**（单个 23MB~125MB），与 `_diag`、`work`、`node_modules` 和源码混在同一层；另有 9 个 `bundle-*`/`render-*` 标签是 9/16 脚本留下的临时产物
- 字体单文件 8~12MB 直接入库（`NotoSerifSC-Bold.otf` 12MB）

**病根**：部署链路要产物、开发要素材、运行时要有状态——三件事都是真的，但被塞进**同一个目录、同一个版本库**。后果不是不好看：clone 变慢、GitHub 推送被掐断（9/21 19:17 就写了「16MB 整目录一次推会被这条链路掐断，实测截断过 sample-poster.mp4」）、每次改动都提交一份新的压缩包进去。

**下次的规矩**

- Day 0 定**三张地皮**并写进 README：源码仓库 / 素材与工作产物（仓库外，或对象存储）/ 状态与密钥（仓库外，生产用挂载路径）。素材包 zip 一律不进仓库根目录。
- 构建产物要上线用，走 **release 或对象存储 + 版本号**；确实必须入库，就用 `git-lfs`，并规定只留最新一份（别把 15 份 bundle.js 焊死在历史里）。
- 依赖与工具链钉版（本项目 9/21 `websockets` 锁到线上实测版本是对的），但**这类事第 2 天做和第 7 天做，成本差一次事故**。
- `.gitignore` 第一天写全，之后每次加东西先问一句「这东西换台机器还能生成吗」——能生成就不进仓库。

**Day 0（半天，不写产品代码）**

## 五、贴墙版：新项目开工 12 条

1. 先定「跑在哪台机器」，再定「长什么样」。
2. 未定的事不许写代码，先写一行决定 + 日期 + 依据。
3. 第 3 个提交装闸门；故意写坏一次，看它拦不拦。
4. 影响钱的数，一律服务端算。
5. 外部服务自报的度量，先自己造真值量一次。
6. 同一症状第二次修，必须换假设，不许调细。
7. 视觉先出样张，选定后令牌封版；一夜只出一套。
8. 一个工作区一个写者；并行就 worktree。
9. 服务器上没有仓库里没有的东西；部署默认只增不删；部署入口只留一个。
10. 能手动一次的不写代码；做两次写脚本；做十次进产品。
11. 产物与素材不进 git 历史；密钥与状态不进工作区。
12. 00:00 之后不做不可逆决策。

## 六、这些数字怎么自己复现

已经把整套指标写成一个脚本，下次开新项目跑一次，五分钟出报告：

```bash
bash tools/git_detour_report.sh . > _diag/detour.txt
```

它数十件事：每日节奏、返工率、深夜提交、同日推翻、建了又删的文件、热点文件、闸门晚到在第几个提交、单体行数膨胀、二进制反复入库、同一模块一天内三个以上 fix（症状补丁链）。本次输出已经存在 `_diag/detour-2026-09-23.txt`。

想手敲单条，最值钱的五条：

```bash
# 返工率：feat : fix
git log --format='%s' | grep -c '^feat' ; git log --format='%s' | grep -c '^fix'

# 同日推翻：这些词每次出现都是一次没写下来的决定
git log --format='%ad %h %s' --date=short | grep -E '退役|下线|拆除|移除|重做|不再|真机|根治'

# 建了又删（那条路本不该走）
git log --diff-filter=A --name-only --format='' | sort -u > /tmp/a
git log --diff-filter=D --name-only --format='' | sort -u > /tmp/b
comm -12 /tmp/a /tmp/b

# 闸门晚到：测试出现在第几个提交
git log --reverse --format='%ad %h %s' --date=short -- 'tests/*' '*/tests/*' | head -1

# 热点文件（单体在这张表的第一行）
git log --pretty=format: --name-only | sed '/^$/d' | sort | uniq -c | sort -rn | head -15
```

## 七、这份报告的局限（免得下次误信它）

- Git 只看得见**提交粒度**。同一个提交里试错八轮、删了重写、会话中途崩掉，历史一个字都不记。所以「返工率 104%」是下界。
- 提交消息是人写的，带自述色彩。写「根治」的那条通常真根治了，写「修一下」的那条最可能明天再修——**别只看 fix 的数量，要看同一个 scope 反复出现的次数**（脚本第 10 条就是数这个）。
- 本项目的 9/15 之前还有一段纯调研期（逆向 Niwo、做素材包、对比成片，见 `项目全过程梳理.md`）。那段时间没进 Git，但它恰恰是全项目**最省钱的一步**：先看懂别人的架构，再决定自己写什么。下次也要给它留位置——只是别忘了当天就把结论 commit 下来。
